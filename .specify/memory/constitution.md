# training-john Constitution

## Core Principles

### Principle 1: CLI Outcomes First
Every enhancement MUST deliver value through a runnable command-line interface that accepts
arguments via standard CLI parsing and emits deterministic stdout/stderr results. Specifications
MUST document the CLI surface before implementation, and releases MAY ship only when the CLI output
is demoable end-to-end.

### Principle 2: Test-Driven Delivery
New behavior MUST start with failing automated tests (unit, integration, or contract) that map to
user stories. Commits MUST not merge unless the new tests pass and existing suites remain at or
above prior coverage. Manual validation MAY supplement tests but never replace them.

### Principle 3: Operational Transparency
Code MUST include observable signals—structured logs, human-readable CLI output, or explicit error
codes—that explain success or failure without inspecting source. Long-running commands MUST report
progress, and all features MUST document how to gather diagnostics in `docs/` or the relevant
feature folder.

### Principle 4: Story-Centered Planning
Specifications, plans, and tasks MUST remain traceable to prioritized user stories. Each story MUST
represent an independently testable slice that can be built, demoed, and potentially shipped on its
own. Work in progress MUST reference the story identifier in branches, commits, and checklists.

### Principle 5: Sustainable Learning Cadence
The team MUST allocate time within each feature cycle for refactoring, journaling, and
retrospectives to capture lessons learned. No change set MAY merge if it introduces unresolved TODOs
without an accompanying backlog task. Training artifacts MUST stay current to prevent knowledge
debt.

## Additional Constraints

- The repository MUST remain JavaScript/TypeScript-first unless a plan documents a cross-language
  integration and gains reviewer approval.
- External APIs or services MUST include offline-friendly fallbacks or mock strategies inside
  `tests/` to keep the learning environment deterministic.
- Artifacts generated by the AI agent (e.g., `.cursor/`) MUST be excluded from version control to
  protect credentials and reduce noise.

## Workflow Standards

- Planning MUST follow the `/speckit.*` command sequence: constitution check → specification → plan
  → tasks → implementation. Deviations MUST be justified in the feature journal.
- Reviews MUST confirm CLI traceability, test coverage alignment, and observability hooks before
  approving.
- Releases MUST summarize story coverage, test status, and outstanding learning items in the weekly
  journal (`docs/` or `journal/`).

## Governance

- Amendments MUST be proposed via pull request referencing impacted stories, templates, and tooling.
- Versioning MUST follow semantic rules: MAJOR for breaking governance changes, MINOR for new
  principles or sections, PATCH for clarifications.
- Compliance reviews MUST occur at the start of each new feature planning cycle and during weekly
  retrospectives.
- Ratification and amendment dates MUST remain in ISO format and update with every approved change.
